# 10월 10일 S1 현장 작업: 3명, 180분

이 문서는 2026-10-08 코드 리뷰를 바탕으로 만든 **방문 제안 기준**이다. 연구원·교수님이 승인한 공식 합격 기준이 아니다. “Robust”라는 말만으로 모든 상황의 주행 보장을 약속하지 않는다. 이번 방문에서는 두 차량의 기본 기능, 입력 실패 시 대응, 재현 가능한 실행 구성과 남은 결함을 남긴다. 실제 노트북·배선·업로드된 펌웨어가 확인되지 않아 180분 안에 모든 기능이 통과한다고 보장할 수 없다.

현재 시험 기준은 **기존 구조의 안전 핫픽스 v2**다. 무수정 원본의 트랙 주행을 먼저 할 필요는 없다. 10월 8일 공지에 따르면 2층 트랙·시험 차량 두 대·완충 배터리·신호등과 리모컨, 302호 우편함의 출입카드 두 개가 준비돼 있다. 배치 완료와 차량 정상 구동은 구분해서 확인한다.

## 처음에 볼 한 장

| 시간 | 강희: 카메라·신호 | 경윤: 제어·아두이노 | 민준: 라이다·기록 |
|---|---|---|---|
| 0–15분 | 기존 노트북과 실행 환경 확인 | 차량 A/B 식별, 전원 차단 수단·조향 기구 확인 | 장치·구성 기록, 기존 실행 프로세스 확인 |
| 15–60분 | 두 영상 방향·차선·빨강/초록 관측 | 바퀴를 띄워 중립·좌우·전후·STOP 확인 | 스캔 방향·장애물 위치·입력 끊김 확인 |
| 60–105분 | 실제 영상 신호 제공 | A차 제한 출력 통합 시험의 **유일한 조작자** | 시험 결과·영상·중단 시점 기록 |

- 세 사람은 작업을 나누되 같은 장치의 드라이버·시리얼 포트를 중복 실행하지 않는다. 센서/영상 관측과 수동 bench 시험은 병행 가능하지만 구동 조작자는 한 명이다.
- 한 문제에서 **15분간 원인이 안 좁혀지면 기록 후 그 기능을 미통과로 둔다.** 멈추지 않는 차량, 배선 불명, 보정 실패이면 해당 차량의 구동 시험을 중단한다. 다른 차의 읽기 전용 점검은 계속할 수 있다.
- F1TENTH 호쿠요 교체 완료는 이 방문의 S1 목표와 분리한다. 제공 부품 확인·간단 교체·반납 준비를 20분 안에 못 끝내면 잔여 작업을 적는다. 구매·11월 일정까지 이 시간에 흡수하지 않는다.
- 한 차가 통과했다고 다른 차의 보정값·장치 ID·핀맵까지 통과한 것으로 간주하지 않는다.

## 전날 결과 하나를 확보할 수 있다면

기존에 차량을 운용한 **그 노트북**에서 기존 ROS/워크스페이스 환경을 연 다음 아래 수집기를 한 번 실행한다. 새 OS·ROS·CUDA를 설치할 필요는 없다. 이 도구는 포트를 열지 않고, ROS 노드나 추론을 띄우지 않으며, 제어 명령을 보내지 않는다.

```bash
python3 /실제/저장소/경로/scripts/s1_preflight.py \
  --workspace /실제/저장소/경로 --output ~/s1_preflight_reports --hash-model
```

경로는 해당 노트북의 것을 사용한다. JSON/TXT에는 ROS 배포판·패키지/모듈·장치별 ID·권한·소스 버전·모델 존재 여부가 담긴다. 종료 코드 0은 수집 성공이지 차량 합격이 아니다. 보고서의 blocker를 먼저 본다. 별칭이 없더라도 실제 `/dev/serial/by-id/…`, `/dev/v4l/by-id/…`로 실행 인자를 지정할 수 있으므로, 그 이유만으로 새 udev 규칙부터 설치하지 않는다.

같이 확보할 정보는 네 가지다: 기존 정상 실행 방법, Arduino에 올린 스케치/보드 정보, 두 차의 장치 연결 사진, 전원 차단 방법. 현재 저장소의 핀맵과 HW 매뉴얼은 다르다. 파일이 있다는 이유로 같은 펌웨어가 차량에 올라가 있다고 가정하지 않는다.

## 후보 코드를 별도 작업공간에서 준비

이 문서와 동봉한 소스는 로컬 `minjune`의 검증 후보다. 기존 차량 워크스페이스를 덮어쓰거나 main을 당겨 바꾸지 않는다. 기존 펌웨어도 자동 업로드하지 않는다. 묶음 파일의 `SOURCE_MANIFEST.json`에는 파일별 해시가 있다.

차량 노트북의 기존 ROS2 환경을 사용한다. 실제 배포판을 확인한 뒤 해당 `/opt/ros/<배포판>/setup.bash`를 연 터미널에서:

```bash
mkdir -p ~/s1_check_20261010/src
# 아래 묶음 경로는 USB 등으로 옮긴 실제 위치로 바꾼다.
tar -xzf /실제/묶음/경로/s1_safety_hotfix_v2_20261008.tar.gz -C ~/s1_check_20261010/src
cd ~/s1_check_20261010
colcon build --symlink-install --packages-up-to s1_stack
source install/setup.bash
```

묶음에는 소스·YOLO 가중치가 포함된다. Ubuntu 패키지, ROS, CUDA, PyTorch 설치 파일까지 포함한 오프라인 실행 환경은 아니다. 전날 빌드/의존성을 확인하지 못하면 현장 설치 시간이 남는다. 빌드가 안 된 상태로 기존 동작 환경을 지우거나 대규모 업그레이드를 하지 않는다.

각 시험용 터미널에서 같은 환경을 연다:

```bash
source ~/s1_check_20261010/install/setup.bash
# 현장의 기존 차와 겹치지 않는 시험용 값인지 먼저 확인한다.
export ROS_DOMAIN_ID=73
export ROS_LOCALHOST_ONLY=1
```

`73`은 예시 시험 도메인이다. 원격 PC와 연결해야 하는 경우 이 localhost 설정을 그대로 쓰면 안 된다. 이번 절차는 기존 노트북에서 직접 실행하는 기준이다. 이미 실행 중인 노드는 환경변수 변경만으로 다른 도메인으로 이동하지 않는다. 해당 차량의 기존 주행 스택을 담당자가 정상 종료한 후 시험한다. 임의로 다른 사람의 프로세스를 일괄 종료하지 않는다.

## 네 가지 실행 단계

| profile | 실행 내용 | Arduino 포트 | 확인 목적 |
|---|---|---|---|
| `sensors` (기본) | 라이다·두 카메라 | 열지 않음 | 장치/영상/스캔 확인 |
| `observe` | 센서·인지·판단 | 열지 않음 | `/s1_check/…`에서 주행 판단만 관측 |
| `manual` | 조이스틱·mux·시리얼 | **열림** | 출력 제한 수동 시험, AUTO 버튼 무효 |
| `auto` | 센서·인지·판단·조이스틱·시리얼 | **열림** | 장애물 없는 구간의 차선·신호 통합 시험 |

`sensors`와 `observe`가 제어 노드를 시작하지 않는다는 뜻이다. 같은 도메인에 남아 있는 다른 제어 스택까지 정지시키는 기능은 없다. observe의 신호/명령/차선변경 플래그는 `/s1_check/` 아래로 분리했다. 단계 전환 시 이전 launch를 정상 종료하여 중복 실행하지 않는다.

장치 별칭이 이미 맞는 경우:

```bash
ros2 launch s1_stack commissioning.launch.py profile:=sensors
```

별칭이 다르면 `arduino_port:=… lidar_port:=… lane_camera:=… front_camera:=…`를 실제 장치 경로로 지정한다. 라이다 baud 기본 256000은 기존 설정을 이어받았으며 장착 모델에 맞는 값인지 확인한다. 필요 시 `lidar_baud:=115200` 등 **확인된 값**을 넣는다. 카메라 `pixel_format:=mjpeg2rgb`도 기존 설정이며 설치된 usb_cam이 지원하는 형식인지 확인한다.

다른 터미널에서 8초 동안 읽기만 하고 결과를 저장한다:

```bash
python3 ~/s1_check_20261010/src/FMTC_intern/scripts/s1_topic_check.py \
  --profile sensors --output ~/s1_field_results/A
```

`--profile`은 현재 단계와 일치시킨다. 수신 Hz·영상 크기·스캔 유효값·마지막 명령·publisher 수를 기록한다. 명령을 발행하지 않는다. `/cmd_auto`나 `/cmd_out`의 publisher가 둘이면 통합 시험을 진행하지 않는다. STOP에서 `/cmd_out`이 조용한 것은 설계된 동작이므로 메시지 0개만으로 고장으로 판정하지 않는다.

### 영상·장애물 관측

```bash
ros2 launch s1_stack commissioning.launch.py profile:=observe
```

`/s1_check/light_stop`, `/s1_check/cross_stop`, `/s1_check/cmd_lane`, `/s1_check/cmd_auto`를 관측한다. 예를 들어 별도 터미널에서 `ros2 topic echo /s1_check/light_stop`을 사용할 수 있다. 실제 빨강·초록 물체/신호판과 카메라 각도에서 검출되는지 강희가 확인한다. 모델 가중치는 설치된 package share에서 찾으며, 다른 모델을 쓸 때만 `model_path:=/실제/모델.pt`를 준다.

관측 규칙: 일반 빨강/노랑은 5프레임 중 3회로 정지하고, 이후 검출이 사라져도 정지를 유지한다. 해제는 서로 다른 새 초록 영상이 연속 3장 수락돼야 한다. 한 영상의 여러 초록 박스는 1표이며, 중복·오래된·처리 중 만료된 영상은 정지 출력한다. 빨강/노랑과 초록이 함께 잡히면 즉시 정지한다. 거리/박스 면적 기준은 기존 것을 유지했으므로 실물 인식 정확도를 이 규칙만으로 합격 처리하지 않는다. 횡단보도는 계속 보이면 계속 정지한다. 몇 초 후 출발이라는 규칙은 새로 만들지 않았다. 자세한 범위는 [공통 신호 핫픽스](signal_hotfix_20261008.md)를 본다.

민준은 물체를 차량 전방/좌우에 놓고 스캔 방향을 대조한다. 기존 회피 ROI는 **센서 좌표 -X의 1.0~1.15m 띠**이며, 가까운 물체 전부를 막아주는 충돌 방지 장치가 아니다. 30점 이상·6스캔 연속 조건과 한 번만 발동하는 플래그를 관측한다. 반복 감지 관측 시 obs_evade를 재시작해야 기존 플래그가 초기화된다. 이를 반복 회피 지원으로 기록하지 않는다.

### 바퀴를 띄운 수동 시험

**시리얼 포트를 열면서 Mega가 리셋되면, 기존 펌웨어도 자동으로 좌우 조향 보정을 한다.** 구동 명령을 아직 보내지 않았다는 이유로 조향이 움직이지 않는다고 가정하지 않는다. 경윤이 실제 배선·기구·전원 차단 수단을 확인하고 시작한다.

```bash
ros2 launch s1_stack commissioning.launch.py profile:=manual max_throttle:=200
```

- 시작은 STOP. 기본 버튼 인덱스는 AUTO 0, MANUAL 1, STOP 3이나 실제 컨트롤러에서 확인한다. 키캡의 글자만 믿지 않는다. 조향 축 0, 구동 축 3도 확인한다.
- `/serial_rx`에서 실제 `CALIB:DONE` 또는 `STATUS:READY`를 확인한다. `/serial_ready`는 보정 응답 수신 상태이지 기계적 안전 인증이 아니다. 응답이 없으면 구동을 허용하지 않는다.
- 보정 성공 뒤에도 새 `TH:0 STN:0` 중립 명령을 확인하기 전에는 구동을 차단한다. `/serial_ready=true`만 보고 출발 가능한 상태라고 해석하지 않는다. 스틱 중립에서 모드를 전환하면 전환 정지 명령이 먼저 전달된다.
- 구형 펌웨어는 `STATUS`를 모르더라도 부팅 시 `CALIB:DONE`을 보낼 수 있다. 그러나 구형은 중앙 복귀 실패에도 DONE을 내보내는 결함이 있다. 물리적 중앙 도달을 경윤이 확인해야 한다.
- 재보정은 실제 조향을 움직인다. 담당자가 필요성을 확인한 경우에만 `/calib/start`를 사용한다. 성공 응답이 없다고 `require_calibration_ack:=false`로 우회하지 않는다.
- 스틱이 중립인 상태에서 MANUAL 전환 후 전후/좌우를 확인한다. 구동 축은 기존처럼 임계값을 넘으면 전출력 요청이지만, 이번 launch의 시리얼 단계에서 **TH ±200으로 제한**한다. 기존 식으로 PWM 최대 36에 해당하며 속도 0.2m/s라는 뜻이 아니다. 마찰 때문에 안 움직일 수도 있다.
- STOP, 조이스틱 노드 종료, 제어 명령 발행 중단, 마지막으로 제어 PC 연결 중단을 구분해서 확인한다. 모든 끊김이 같은 경로로 정지하지 않는다. Python 송신기만 살아 있으면 명령 만료 0.3초 설정 후 정지 한 번을 보내며, PC/USB 자체가 끊기면 펌웨어의 2초 watchdog에 의존한다. 실제 바퀴 정지는 따로 측정한다.
- STOP/timeout의 `TH:0 STN:0`은 구동 출력 0과 조향 중앙 요청이다. 즉시 모든 모터 전원이 꺼진다는 뜻이 아니다. **실제로 패킷 전송이 끊긴 경우에** 이후 무신호 watchdog이 조향을 비활성화한다. 수동 조이스틱 입력 만료처럼 상위 노드가 0을 계속 보내는 경로에서는 조향 중앙 제어가 유지될 수 있다.

후보 펌웨어는 보정 실패 구동 차단, 중앙 도달 실패 검출, 보정 중 쌓인 명령 폐기 등이 추가됐다. **실차 핀맵 확인·기존 스케치 백업·Mega용 빌드가 되기 전에는 업로드하지 않는다.** 현장에서 이 조건을 확인할 수 없으면 “펌웨어 수정 미적용”을 결과에 남긴다. 기존 배선을 매뉴얼 그림에 맞춰 바꾸지 않는다.

### 제한된 통합 주행

수동 방향·정지가 통과하고, 강희/민준의 입력 관측이 정상일 때 장애물 없는 통제된 구간에서:

```bash
ros2 launch s1_stack commissioning.launch.py profile:=auto max_throttle:=200
```

조이스틱 AUTO 버튼으로 선택한다. 라이다의 사용 가능한 입력, 차선 명령, 두 신호 판단이 없거나 오래되면 구동 0이 된다. 차선 미검출도 구동 0이다. AUTO 중 조이스틱 메시지가 끊기면 STOP으로 전환하고 재선택이 필요하다. 차선/신호/라이다 입력 회복은 자동으로 주행 판단을 재개할 수 있으므로 시험 중단 시 담당자가 STOP을 선택한다.

기본 `auto`는 **회피를 실행하지 않는다.** 기존 4초 회피를 검증하려면 별도 넓은 공간에서 `enable_evasion:=true`를 명시하고, 한 번 수행 후 영구 플래그·조향 방향·경로 이탈을 확인한다. 장애물 없는 차선/신호 시험 통과를 장애물 회피 합격으로 적지 않는다. 3시간을 지키려면 회피가 안 되는 이유까지 기록하고 당일 새 회피 알고리즘을 만들지 않는다.

## 합격/미통과를 기록하는 기준

기본 시험은 차마다 3회 반복하되, 반복 횟수만으로 신뢰성 통계를 주장하지 않는다. 한 번이라도 의도와 다르면 실패 상황·로그를 남긴다.

| 항목 | 확인할 관측 | 현재 로컬 검사와 구분할 것 |
|---|---|---|
| 수동·중립 | 전후/좌우가 의도와 맞음, 중립·STOP에서 구동 0 | 실제 방향·속도·제동 거리는 현장값 |
| 빨간불 | 실제 영상 인식 후 구동 0, 가려도 정지 유지, 초록 확인 시 해제 | Bool 주입 성공만으로 영상 인식 성공 처리 금지 |
| 차선 실패 | 차선을 가린 영상에서 구동 0 | 카메라 메시지가 살아 있는 상황도 포함 |
| 입력 실패 | 차선/신호/scan 각각 중단 시 구동 0, AUTO 조이스틱 중단 시 STOP | 노드 중단·USB 분리·PC 종료를 별개 기록 |
| 아두이노 준비 | 보정 실패/미확인 시 주행 안 함, 보정 성공과 중앙 일치 | 실제 구형 펌웨어 적용 여부 명시 |
| 라이다 | 센서 방향·거리와 실물 위치 일치, 결측 시 멈춤 | “유효 scan 있음”은 “경로에 장애물 없음”이 아님 |
| 회피 | 트리거·조향·회복을 별도 관측 | 1회 회피만 있는 기존 한계, 미시험이면 그대로 기록 |
| 재실행 | 정상 종료 후 다시 실행하여 같은 단계 수행 | 두 차의 장치 경로/모델/프로필 각각 저장 |

실패 대응을 확인할 때 처음에는 바퀴를 띄운 상태로 한다. 바닥에서 확인할 물리적 정지거리·차선 유지 구간·신호 인식거리는 현장 트랙과 차량 상태를 보고 기록한다. 이 문서에서 측정하지 않은 숫자를 합격치로 발명하지 않는다.

기록지는 `docs/field_results_template.csv`를 A/B 각각 복사해 작성한다. `PASS/FAIL/NOT_TESTED/BLOCKED`와 증거 파일을 함께 남긴다. 마무리 때는 “Robust 완료” 대신 **어떤 구성으로 어떤 시험을 통과했고 무엇이 미확인인지** 한 문장으로 전달한다.

## 지금까지 확인한 범위

로컬 검사는 실제 Python 콜백과 실제 `.ino` 코드를 대체 ROS/시리얼/GPIO 환경에서 실행한다. 가상 트랙은 사용하지 않는다. macOS에서 ROS/DDS·USB·카메라 추론·AVR 바이너리·물리적 제동을 검증한 것은 아니다. 기존 리뷰 기록은 작업 기지 `reports/s1_function_review_20261008/`에 별도 보존되어 있으며, 그 기록의 결함 재현 결과와 이번 수정본의 회귀 검증 결과를 섞지 않는다.
